# kcp-cpp

C++17 port of [xtaci/kcp-go](https://github.com/xtaci/kcp-go) v5: KCP ARQ core, FEC (Reed-Solomon),
block crypto (CFB variants + AES-GCM), and the UDP session/listener layer.

Goal: **wire-compatible** with kcp-go, zero third-party dependencies.

The porting plan (scope, wire formats, golden vectors, gates, deviations) lives in
[`PORTING-PLAN.md`](PORTING-PLAN.md). Every wire-format statement in that document carries a
kcp-go source line number; when code and plan disagree, the plan's line reference decides.

## Build

Windows (MSVC):

```bat
build.bat            rem Release
build.bat Debug
```

Linux (Ninja + GCC/Clang):

```sh
./build.sh           # Debug
./build.sh Release
```

`build.bat` runs, in order: configure, build, `check_guard.py` (Google `#define` guards, no
`#pragma once`), `check_format.py` (clang-format, Google + 100 columns), then `ctest`. A build that
only compiles is not a passing build.

## Golden vectors

`tools/golden` emits byte-level vectors from the reference implementation. The emitter lives in
`ref/golden_ref.go.txt` and is injected into the kcp-go package with `go test -overlay`, because the
FEC layer and the CFB initial vector are unexported; this keeps the reference checkout untouched.
C++ tests compare against the committed `out/*.json`; a mismatch means a porting bug, never a vector
bug. Regenerate with:

```bat
cd tools\golden && gen.bat
```

| vector | what it pins |
|---|---|
| `crypt.json` | every cipher, both AES backends, unaligned CFB lengths |
| `rs.json` | Vandermonde matrix head, systematic encode |
| `fec.json` | 13-shard encode, variable-length second round, recovery |
| `kcp.json` | segment bytes for the KCP state machine over a scripted tick sequence |
| `frame.json` | the assembled four-layer datagram: 6 configurations, byte for byte |

## Throughput

`bench.md` is generated by `python tools/bench/run_bench.py` (5 rounds per cell, first round
dropped, median reported). It drives `examples/echo_*` and `tools/interop/goecho_*` with **identical
parameters** — conv=1, mtu 1400, no-delay(1,10,2,1), snd/rcv window 32/32 — because the kcp-go
defaults differ from the ported ones and a baseline with different defaults is not a baseline.

Headline numbers on Windows x64 loopback (median of 5, `bench.md`, 2026-10-18 late session):

| config | C++ single | Go single | C++ 10 streams | Go 10 streams |
|---|---|---|---|---|
| none, fec off | 111.7 MB/s | 118.6 MB/s | 64.0 MB/s | 65.5 MB/s |
| aes-gcm, fec 10/3 | 45.7 MB/s | 147.0 MB/s | 36.0 MB/s | 66.6 MB/s |
| salsa20, fec 10/3 | 59.6 MB/s | 85.5 MB/s | 46.3 MB/s | 64.6 MB/s |

**Machine-state caveat (measured, not assumed)**: the same workload on this machine varies ±30%
between clean runs (109.5 / 111.7 / 160.5 MB/s for `none` single across three baselines, while
within-run min/max is ±1%). Quote a baseline only together with its `bench/syscall_cost`
calibration line — that is the fingerprint of the machine state it was taken in. The numbers above
are from one 5-round run; re-run before drawing conclusions.

**Attribution, measured rather than argued** — P8.0 (`tools/bench/profile_split.py`) decomposes one
100 MiB run into five CPU budgets (read thread / post thread / update callback / writer / reader)
plus per-syscall counts, and the books close within 10% of process CPU (-0.8% to -2.5% across the
three configs). For `none fec=0/0` at 148.6 MB/s in one profiled run:

* **13.3 µs CPU per datagram, spread evenly**: read thread 33% (`recvfrom` + decrypt +
  `Kcp::Input`), post thread 33% (FEC + CRC + encrypt + `Tx`), reader 30% (`read` + verify),
  writer 2% (`write` → `Kcp::Send`), update callback ~0%.
* **Syscalls are a small slice**: `sendto` 2.88 µs/call, `recvfrom` 0.63, readiness probe 1.08 —
  together ~4.7 µs of the 5.1 µs wall per datagram, and a minor part of the 13.3 µs CPU. There is
  no single dominant segment left to attack, which is why every P8 item below carries a trigger.
* Still true from P6: the protocol engine is not the limit (`bench/kcp_pump`, 0.8–2.1 GB/s) and
  the read path is not the limit.
* A previous attribution of this section — "`sendto` costs 41–46 µs, 15–17x `WSASendTo`, hence
  112 µs/datagram" — was measured during a busy-machine window on 2026-10-18 evening and **does
  not reproduce**: same machine, same code (verified against the committed build, 109.5 MB/s),
  `sendto` prices at 3.4 µs today and the API gap is 1.3x. The Go↔Go baseline was stable across
  both windows (119.5 → 118.6 MB/s) while the C++ client — four threads — collapsed 10x under
  load where Go's IOCP client did not: thread-heavy implementations fall over first on a busy
  machine. Kept here as a record; `PORTING-PLAN.md` §6.3.1/§6.3.2 carry the full story.

Two numbers that look like regressions but are not, both recorded so nobody re-litigates them:

* **One-way (`-discard`) is far slower than echo** (2.48 MB/s in the P6 window). With nothing to
  send back the receiver's ACKs cannot piggyback, so they wait for the `interval`=10 ms flush
  tick, which the Windows timer granularity stretches to ~17 ms. That is KCP's design, not this
  port's.
* **AES-GCM's AES-NI advantage is only 1.37x, not 3.81x.** GHASH is a 4-bit table
  (`src/internal/gcm.cc:81-113`) with no PCLMULQDQ path yet. At 168 MB/s against a 45.7 MB/s
  session it is not yet the bottleneck (P8.5's trigger includes its precondition chain, which has
  not happened).

P8 in `PORTING-PLAN.md`, after P8.0's table:

1. **P8.0 — done.** Instrumentation (`kcp::UdpSession::EnableProfiling`), the fold script
   (`tools/bench/profile_split.py`), and the §6.3.2 ledger. Its finding: the 25 MB/s target line
   is already exceeded 4.5x, and no single segment dominates.
2. **P8.1** `sendto` → `WSASendTo`: **trigger invalidated** — the 15–17x gap is 1.3x today
   (~1 µs/datagram). Recorded as "not the bottleneck now", not implemented.
3. **P8.2** drop the per-datagram `select(0)` probe: read-path syscalls are <15% of CPU — trigger
   not met.
4. **P8.3** IOCP: only if I/O waiting still exceeds 30% of per-datagram cost after P8.1 — there is
   no such waiting to save.
5. **P8.4** `recvmmsg`/`sendmmsg` on Linux (D4) — Linux only, and only once E1 can run.
6. **P8.5** GHASH via PCLMULQDQ, **P8.6** RS views — triggers not met (see PORTING-PLAN.md
   §6.3.2 for the per-item arithmetic).

## Tests

`ctest` runs 16 binaries. The ones that carry behaviour rather than vectors:

* `session_test` — loopback for plain / FEC+GCM / FEC+Salsa20, 10 concurrent sessions on one
  listener, message boundaries, all three `read` paths, close-unblocks-read, tail flush on close,
  deadlines, socket option matrix, MTU bounds, `curr_estab` accounting, listener-closes-children,
  and a listener surviving a peer that disappears mid-transfer.
* `relay_test` — real UDP relay (`tests/lossy_relay.{h,cc}`, two sockets, two threads, no reordering
  or corruption) across clean / 10% uniform / 30% uniform / Gilbert-Elliott.

Two P6 defects are worth knowing about because they were invisible to every single-connection test:

1. `Listener::Monitor` treated `recvfrom` errors as fatal. On Windows a peer closing mid-transfer
   raises ICMP port-unreachable, which the *next* `recvfrom` reports as `WSAECONNRESET` — so the
   monitor thread exited and **every** session on that listener starved at once. kcp-go never
   returns from its read loops; now neither does this one.
2. `Listener::close()` did not close its child sessions, so they outlived the listener's session map
   and their destructors erased from freed memory: `STATUS_HEAP_CORRUPTION` about one run in ten.

Both are pinned by tests, and both tests were verified by reverting the fix and watching them fail.
The lesson is in PORTING-PLAN.md R22: concurrency defects in shared resources need a
*one listener + N sessions* shape to show up at all.

## Cross-language acceptance

`matrix.md` is generated by `python tools/interop/run_matrix.py` (3 rounds per cell):

```
cpp->go  none fec=0/0     PASS    cpp->go  aes fec=10/3    PASS
cpp->go  none fec=10/3    PASS    cpp->go  aes-gcm fec=0/0  PASS    ...  16 cells
go->cpp  none fec=0/0     PASS    go->cpp  salsa20 fec=10/3 PASS
```

Every cell asserts three things, and all three have to hold:

1. the echo comes back byte-for-byte — the expected SHA-256 is computed by the runner in Python from
   the payload rule (`payload[i] = i*7 + 11`), not copied from either implementation, so two
   implementations that are wrong in the same way cannot agree their way past it;
2. both directions carry data (one echo covers both);
3. **the first datagram is byte-identical on both sides** — `--dump-dir` captures what the sender put
   on the wire and what the receiver took off it, and reports the first differing offset if they
   differ. 48 captures, all identical.

`tools/interop/dump_packet.py` is the §6.1 localization tool: `--decode` walks one capture through
the §4 layout (cipher header → FEC header → KCP segment), and passing two files diffs them with ±32
bytes of context. One thing it makes visible: **`crypt=none` still carries a 20-byte header** —
`NoneBlockCrypt` only turns `Encrypt` into a no-op, the nonce and CRC32 are still written. A zero
header only happens when no crypt object is installed at all (`kcp::Listen` / `kcp::Dial`), which
matches kcp-go's `Dial`.

## Conventions

Google C++ Style with one recorded deviation (D8: 100-column limit). Files are `.h` / `.cc`,
headers use `#define KCP_*_H_` guards (`#pragma once` is forbidden), and every ported file keeps the
upstream MIT header. Deviations from kcp-go behavior are listed in PORTING-PLAN.md §3.4.1 (D1–D19)
and must be extended before adding a new one.

`tools/interop` holds the Go echo server/client used for cross-language acceptance (P7) and for the
Go<->Go baseline the C++ numbers are compared against. Both endpoints bind `127.0.0.1` by default, so
the test matrix never needs a firewall rule.
