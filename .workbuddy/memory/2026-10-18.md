### 两个致命缺陷（都在"照抄 Go 没抄到底"）

1. `Listener::Monitor` 把 `recvfrom` 错误当致命，`return` 后整个 listener 上所有会话饿死。
   Windows 把对端关闭引发的 ICMP 端口不可达报成下一次 `recvfrom` 的 `WSAECONNRESET`(10054)。
   修法照 kcp-go：计数后继续读。
2. `Listener::close()` 不关子会话 → `sessions_` 先析构，会话析构再回调 `CloseSession()` 擦已释放的 map
   → `STATUS_HEAP_CORRUPTION`（约 1/10）。修法照 kcp-go `Listener.Close`：先关全部子会话再关 fd。

两处都做了变异回退验证（改回去测试必失败）。**教训**：并发缺陷只能用「1 listener + N 会话」压测形态复现，
单连形态 160 次全绿、并发 15/40 失败。已登记为 PORTING-PLAN.md R22。

### 性能归因（推翻了之前的结论）

- 旧结论"12 MB/s ≈ 平台往返上限的 83%"**算法是错的**：把成批流水的段按每段一次往返折算。
- 窗口 32/128/512 → 13.1/13.5/12.2 MB/s，吞吐不随窗口变 → 不是窗口×RTT。
- 真因：每数据报固定 I/O 成本。4.07 万数据报/秒 ≈ 24.6 µs/数据报；Go 同参数 5.5 µs（IOCP + goroutine 1 µs 交接）。
- `bench/kcp_pump` 0.8~2.2 GB/s、`aes_bench` CFB 1262 MB/s → 引擎与加密都不是瓶颈。
- `-discard` 单向仅 2.48 MB/s：接收侧无数据可捎带 ACK，只能走 interval=10ms 的 flush tick，被 Windows
  定时器粒度放大到 ≈17ms。KCP 协议本身性质，非缺陷。
- GHASH 仍是 4-bit 查表（`src/internal/gcm.cc:81-113`，无 PCLMULQDQ），GCM 168 MB/s，只比 T 表快 1.37x。
  已列 P8。
